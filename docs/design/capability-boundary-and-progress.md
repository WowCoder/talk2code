# 能力边界声明与执行进度可观测化

本文档记录四项设计的最终态：能力边界声明、动作级进度模型、单轮长尾熔断、
品类 Skill 目录。四者共同解决同一类问题——**系统知道自己能做什么、正在做什么，
但用户不知道**。

## 1. 能力边界必须对用户可见

### 问题

本平台的产出形态是纯静态前端站点（唯一权威定义见
`harness/constraints/environment_contract.py` 的 ENV-1~ENV-6）。这个边界此前
只写在给模型的 prompt 里，面向用户的澄清链路完全没有对应声明。

后果不是报错，而是**静默降级**：用户提出需要服务端的需求时，意图分类器没有
「超出能力范围」这一类，需求照常进入开发流程，最终交付一个用本地存储伪造的
实现。验收不通过时前端也不说明真实原因，用户得到的印象是「这个平台做不好」，
而不是「这个平台不做后端」。

### 设计

边界声明拆成三层，缺一层链路就断：

| 层 | 位置 | 作用 |
|---|---|---|
| 分类器 | `prompts/intent/classify.md` 的 `OUT_OF_SCOPE` | 识别「核心功能依赖服务端」的需求 |
| 澄清 | `prompts/intent/clarify_generate.md` 的 `data_scope` 问题 | 讲清边界并给出可选方案 |
| 兜底 | `requirement_service.OUT_OF_SCOPE_QUESTIONS` | 分类未命中时，澄清环节仍能补上 |

**关键取舍：不直接拒绝。** 用户说「要后端」，真实意图通常是「数据要存下来」
或「要能多人看到」，一句「做不到」把需求堵死；而「本地存储版 + 讲清局限」
既守住边界又给得出东西。因此 `data_scope` 的三个选项都刻意写成可交付形态：

- 改成浏览器本地存储（功能完整，数据在本机）
- 内置示例数据做演示（重点看界面和交互）
- 只做界面与交互（数据留空接口，后续自接后端）

用户选完即可开工，不需要再追问一轮。

### 判据

「做不到」的判定标准是**需求的核心价值**是否建立在服务端能力上：
服务端数据库、真实账号体系、跨设备同步、后端接口、实时通信、
第三方 API 密钥调用、支付与短信、爬虫与定时任务。

凡是能用本地存储等价满足的仍是正常开发需求——「能保存我的任务的待办清单」
不需要服务端。分类器的默认倾向是 TASK，避免滥用 OUT_OF_SCOPE。

## 2. 动作级进度模型

### 问题

后端一直在发中间事件（SSE `progress`），但两处设计让用户几乎看不到：

1. **推送的是角色名，不是动作**。「开发工程师工作中」不携带任何进展信息。
2. **编码阶段零推送**。进度推送整段包在 `if contract and contract.exists()`
   内，契约文件缺失时整个编码期没有任何事件，前端只能显示静态文案。

### 设计

进度事件从「角色 + 百分比」扩展为「**动作 + 阶段 + 百分比**」，并补齐埋点：

| 阶段 | 埋点位置 | 文案形态 |
|---|---|---|
| planning | 节点进度映射 | 正在分析需求，拆解实现计划 |
| coding | 工具执行前（白名单工具） | 正在创建 js/app.js |
| coding | 文件写入成功（无契约也推） | 已完成 js/app.js（2/4） |
| verifying | 浏览器会话前 / AC 循环前 / 冒烟前 | 正在逐条验证 5 条验收标准 |
| repairing | 节点进度映射 | 正在修复发现的问题 |

两条规则：

- **文案描述动作，不描述角色**。角色名不携带进展信息。
- **推送不设前提条件**。契约只让文案能带 `(n/total)`，不是推送的前提。

工具白名单（`runtime.ToolCallLoop._ACTIVITY_TOOLS`）刻意排除了 `read_file`
和 `list_files`：它们高频且对用户无进展信息，推送只会刷屏。

### 前端呈现

进度展示放在对话区（用户视线焦点），包含三部分：

1. 当前动作文案——直接取 `progress.current_agent`；
2. 阶段指示器——需求分析 / 编码 / 验证 / 修复，当前阶段高亮、已完成划线；
3. 静默期计时——当前动作持续超过 15 秒后显示「已等待 N 秒」。

第三项针对的是 LLM 挂起：静默期可能长达数十秒且无任何业务事件，
此前用户只能面对一个不动的界面。「这一步跑了多久」比转圈更能回答
「是不是卡住了」。

## 3. 单轮长尾熔断

### 依据

统计 12 个真实需求共 155 轮 LLM 调用：

| 指标 | 实测 |
|---|---|
| 端到端耗时 | 中位 12.7 分钟 |
| LLM 占比 | 63% |
| 单轮延迟 | 中位 11.4s / p90 101s / max 316s |
| 慢轮次（>60s） | 占 20%，吃掉 71% 的 LLM 总时间，输出却很短（中位 583 token） |

慢轮次输出很短，说明是空转或端点抖动，不是「在生成很长的代码」。
因此优化杠杆不是少写点，而是别在空转的轮次上干等。

### 设计

编码阶段单轮 LLM 给定一个预算（默认 45s，配置项 `LLM_SLOW_TURN_TIMEOUT`）：

1. 首试带预算，且**关闭客户端内部重试**——否则实际墙钟是预算的 N+1 倍，
   熔断形同虚设；
2. 仅当失败原因是超时才重试一次，用减半的 `max_tokens` 降级；
3. 第二次不设预算、走实例默认重试——不无限熔断，避免误杀真的需要长输出的轮次；
4. 配置为 0 时整体关闭。

## 4. 品类 Skill 目录

Skill 机制本身是声明式的：`prompts/skills/<name>/` 下放 `manifest.json`
（含 trigger 正则与 priority）和 `SKILL.md`，加载器按正则确定性匹配、
按 priority 排序注入编码 prompt，选型不消耗 LLM 调用。

缺口在**品类覆盖**：此前只有一个 `game` 品类 skill，其余都是配色、排版、
无障碍这类通用素养——于是「做个待办清单」和「做个数据看板」拿到同一套套路。

现补齐六个品类：

| Skill | 覆盖 | 核心约束 |
|---|---|---|
| `crud` | 待办、记账、博客、通讯录 | 存储层独立、表单 id 与 HTML 对账、渲染由数据驱动、空态 |
| `tool` | 计算器、转换器、格式化、编解码 | 输出区占位、边界输入给反馈、复制功能降级 |
| `dashboard` | 看板、统计报表、可视化 | 零 CDN 手绘 SVG 图表、容器尺寸兜底、空数据态 |
| `landing` | 官网、落地页、作品集 | 首屏完整可见、零外链资源、响应式、锚点偏移 |
| `admin` | 管理后台、运营平台 | 菜单切换真的换内容、纯前端分页排序、弹窗状态重置 |
| `game` | 各类小游戏 | 启动流程、就绪态与循环启动成对、遮罩层闭环 |

约束：一个需求**最多命中一个品类 skill**。品类正文不短，多重注入会撑大
prompt，而 prompt 每轮都要重发（中位已达 13.7k tokens），长度即固定成本。
`tests/unit/test_skill_catalog.py` 守这条互斥性。

## 5. 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `LLM_SLOW_TURN_TIMEOUT` | 45 | 单轮 LLM 熔断预算（秒），0 = 关闭 |

## 6. 未纳入本轮

- **验证阶段浏览器会话合并**：当前一次验证会启动 4 次独立 Chromium 会话
  （预览、AC 验收、通用冒烟、截图），最坏合计约 10 分钟。合并为一个会话、
  AC 并行执行可显著提速，但要改动会话线程隔离这一高危机制，需单独验证。
- **进度事件落库**：目前中间事件只走 SSE 内存广播，刷新页面后不可恢复。
  需给 `requirements` 表增加进度字段并配套轮询兜底。

## 7. 验收口径

以两条硬指标衡量迭代效果：

1. 端到端耗时中位下降到 6 分钟以内；
2. 任意时刻前端都能说出后台正在做什么（不存在只显示通用文案的阶段）。
