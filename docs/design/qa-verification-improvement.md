## 1. 结论先行

当前验收**不是「不准」，是「不知道准不准」**。它有四类结构性缺口，其中一类会直接产生假绿；
而更根本的问题是：**项目里没有任何指标能回答「这些 AC 到底有没有在守卫」**。

## 1.1 P0 已执行：实测结论（2026-09-23）

数据源：`backend/workspaces/*/*/.task/evaluator/result.json` 的 `ac_results`
（28 个任务 / 139 条 AC）。脚本：`tmp/analyze_ac_verification.py`（只读）。

**2×2 交叉矩阵（脚本是否跑成 × 断言是否失败）**

| | 条数 | 占比 | 含义 |
|---|---|---|---|
| 脚本跑成 + 无失败 | 27 | 19.4% | **可信通过** |
| 脚本跑成 + 有失败 | 40 | 28.8% | **可信失败**（真缺陷信号） |
| 脚本没跑成 + 无失败 | 6 | 4.3% | 假绿（S1） |
| 脚本没跑成 + 有失败 | **63** | **45.3%** | **不可信失败**（幽灵信号） |

**三条结论：**

1. **假绿只有 4.3%，低于 5% 判据 → S1 不是当务之急。**
   而且这 4 个含未验证 AC 的任务**最终全部判 NEEDS_WORK**，无一被放行。
2. **真正的大头是 45.3% 的「不可信失败」**。这些 AC 的断言是在**脚本没能完整驱动**的
   页面上跑出来的，失败可能是幽灵。它会让 repair 轮追着不存在的问题改 ——
   这是对通过率伤害最大的一条，而且此前完全没有量化。
3. **只有 48.2% 的 AC 执行是「脚本完整跑成」的**（27+40=67/139）。
   超过一半的 AC 脚本有步骤失败。

**样本偏差（必须注明）**：这 28 个任务里 23 个最终判 NEEDS_WORK、只有 5 个 PASS，
样本偏向失败任务，所以 74% 的失败率**不代表线上整体水平**。
但 2×2 的**比例结构**仍然有效 —— 它说明「脚本跑不成」是一个高频现象，与任务成败无关。

## 2. 现状：验收链路的四层信号

```
① 静态契约检查（零浏览器、零 LLM）  ENV-2/3/6 + 跨文件 API 闭合 + DOM-id 契约
② 浏览器运行时                      pageerror / console_error / requestfailed
③ AC 逐条验收                       LLM 翻译一次 → Playwright 脚本缓存 → 多轮重放
④ 通用冒烟四不变量                  self_contained / interactive / no_instant_death / storage_safe
        ↓ 融合判定
   快速通道（全绿 → PASS，UI 与代码质量置 null）
   或 双视角 LLM 评估
        ↓ 兜底
   确定性证据覆盖模型判定
```

**四条必须保留的设计**（重构时别误删）：

1. **验证环境与用户环境等价** —— 走 `/api/pt/` 能力 URL + sandbox iframe，而不是直接开文件。
   `nodes.py:1172` 的注释就一句「杜绝验证过、用户废」。这是整套系统的灵魂。
2. **AC 脚本首轮锁定**（`nodes.py:1188-1207`，按 `ac_hash` 缓存）—— 防同一份代码每轮结果漂移。
3. **`failures` vs `harness_errors` 二分** —— 防假阴压垮验收。
4. **确定性证据覆盖 LLM 判定** —— 日志实证多次触发：
   `LLM 判定 PASS 被确定性证据推翻(冒烟=X, AC失败=Y) → 强制 NEEDS_WORK`。

这套东西是真踩坑长出来的，代码里刻着事故编号：
需求 124（跨文件 API 断裂）、126（选择器漂移）、127（误报修正）、132（DOM-id 契约）、
140（假绿 + 内层 document 按键）。

## 3. 覆盖率审计：四类结构性缺口

### S 级 —— 会产生假绿（坏东西被判通过）

**S1. `harness_errors` 不阻断 `passed`（最严重）**

`preview_runner.py:518` 的判定是 `"passed": len(failures) == 0`。
若一条 AC 的所有步骤都因选择器失配抛异常，它们**全部**进 `harness_failures`（:510），
`failures` 为空 ⇒ **passed = True**。

- 缓解只覆盖一半：`nodes.py:1292` 的 `ac_all_passed` 额外要求 `not r.get("harness_errors")`，
  所以**只有快速通道**被拦住
- 走 LLM 评估通道时，脚本错误仅以 `[脚本错误·可能假阴性]` 文本附给 LLM 作「定性判断」
  （`nodes.py:1380`），**不阻断**
- 叠加 AC 脚本首轮锁定 ⇒ **选择器一旦写错，整条 AC 在整个 repair 循环里恒过**

**S2. `assert_canvas_change` 只判「变了」，不判「对不对」**（:496-503）

比的是 canvas 像素哈希前后不同。画一团乱码、画错颜色、蛇身断裂，只要像素变了就通过。
而旗舰演示 req76 正是 canvas 游戏。

**S3. `_resolve_selector` 的模糊匹配会张冠李戴**（:259，需求 126 事故）

为修「AC 写 `#start-btn` 但产物是 `startBtn`」的假阴，改成关键词模糊匹配 id/class/文本。
代价是可能把断言匹配到**另一个元素**上 —— AC 在测一个不是目标的东西，还显示通过。
**典型的治假阴引假阳。**

### A 级 —— 覆盖不到，但结果诚实

- **A1 视觉与审美完全不覆盖**。快速通道明确把 `ui_quality`/`code_quality` 置 null
  （`nodes.py:1298-1300`，注释：「不再用硬编码 8/9.2 伪装视觉质量已评」）。诚实，但就是没验。
- **A2 AC 之间状态不连续**。每条 AC 都 `_load()` 重载（:416），
  「添加 → 刷新 → 还在」这类跨步骤 AC 验不了。
- **A3 只有固定 `wait ms`，无轮询等待**。慢加载会假阴 → 进 harness_errors → 回落 S1。

### B 级 —— 断言语义太弱

- **B1** `assert_text` 只做子串包含，不校验数值关系
  （「合计 123」与「页面某处出现 123」无法区分）。
- **B2** `assert_count` 只支持 `≥ min_count`，不支持「恰好」和「顺序」。

## 4. P0：先量化，再动手

在改任何代码之前，先用现有数据回答三个问题。**这一步半天就能做完，且决定了后面要不要动。**

| 指标 | 怎么算 | 数据在哪 |
|---|---|---|
| 未验证 AC 占比 | `failures==0 且 harness_errors>0` 的 AC 条数 / 总 AC 条数 | 各任务 `.task/` 产物 + `server.log` |
| 恒过 AC 嫌疑 | 同上，且该条在**所有 repair 轮**都保持此状态 | 同上 |
| 快速通道占比 | 走 fast_pass 的任务数 / 总任务数 | `server.log` 的「快速通道」行 |

**判据**：如果「未验证 AC 占比」低于 5%，S1 只是理论风险，优先级下调；
如果高于 15%，S1 就是正在发生的假绿，必须马上修。

## 5. 优化项设计

### P1：`harness_errors` 不再默默通过 —— ✅ 已实现（未提交）

**实测发现：这项改动已经在当前工作树里了**，不需要重写。
`git diff backend/harness/tools/preview_runner.py` 可见：

```diff
-   "passed": len(failures) == 0,
+   # 脚本驱动失败（harness_errors）同样阻断 passed：选择器超时 / 元素点不动
+   # 意味着这条 AC 从未被真正验证过，此时判 passed=True 是假绿
+   #（req 145 的 AC-1/AC-4 就是带着 harness_errors 拿到 passed）。
+   "passed": len(failures) == 0 and not harness_failures and not not_applicable,
```

顺带还做了两件超出原计划的事（来自 req 147 复盘）：

- 新增 `not_applicable` / `unverified` 通道：页面无 canvas 却断言 canvas 变化时，
  记为「断言前提不成立」而不是硬失败或脚本错误（修的是 §3 的 S2）
- 新增 `assert_dom_change` 动作：DOM 实现的画面类 AC 原先被译成 `assert_canvas_change`，
  结果永远是「不适用」，现在有真正的 DOM 变更断言可走

**还差两件事**（原计划里的配套，尚未落地）：

1. **测试**：未见针对「所有步骤抛异常时 `passed is False`」的用例。按 TDD 纪律要补。
2. **措辞不一致**：`nodes.py:1448` 仍把 harness 错误写成
   「假阴性嫌疑，**不计入产品缺陷**，供定性判断」。但 `passed` 现在会因为 harness 错误变 False ——
   判定说没过、提示词说别当缺陷，两处互相打架，LLM 很可能据此判 PASS。
   需要改成「这些 AC 未能完成验证，不得视为通过」。

**下面的三态设计仍然作为文档口径保留**：

| status | 条件 | 含义 |
|---|---|---|
| `pass` | `failures` 空 **且** `harness_errors` 空 | 真的验过了，真的通过了 |
| `fail` | `failures` 非空 | 产品缺陷 |
| `unverified` | `failures` 空 **但** `harness_errors` 非空 | **没验成，不等于通过** |

**兼容性**：`passed` 保留为 `status == "pass"` 的简写，现有调用方
（前端 checklist、`nodes.py:1365` 的 LLM 文本）不需要改。
`ac_all_passed` 的语义本来就已经要求无 `harness_errors`，所以**快速通道行为不变**。

**关键的两处配套改动**（缺一不可，否则改了等于没改）：

1. **LLM 评估通道的提示词必须改**：现在 harness 错误被写成
   `[脚本错误·可能假阴性]` 供「定性判断」，措辞太软。改成明确指令：
   *「以下 AC 未能完成验证，不得视为通过；如果总数中 unverified 占比高，
   整体结论应降级为 NEEDS_WORK 而不是 PASS。」*
2. **unverified 必须回灌 repair 循环**，让 coder 有机会修（现在的 hints 只是附件文本）。
   否则选择器写错会一路恒过到 `max_rounds`。

**验证**：新增测试断言「所有步骤都抛异常时 `status == "unverified"` 且 `passed is False`」。

**风险**：`unverified` 变多会让通过率**短期下降**。这是预期内的 —— 它本来就该是红的。

### P2：变异测试，产出「AC 有效率」

**思路**（借 SWE-bench 的 FAIL_TO_PASS）：先确认这条测试在坏代码上**确实会红**。
我们从未验证过 AC 的**可证伪性**。一条恒过的 AC 和没有 AC 是一回事，
而现在没有任何指标能区分这两者。

**工具**：`tmp/mutation_test.py`（`cd backend && python3 ../tmp/mutation_test.py --limit 6`）

**菌株设计原则（关键）**：**语法必须仍然成立**。

如果变异把 JS 改成语法错误，页面直接白屏，那是被 console error 抓到而不是被 AC 抓到，
会把 AC 有效率算虚高。所以四个菌株都保证「页面照常加载、逻辑静默出错」——
这也正是最难发现、最需要 AC 去守的那类 bug：

| 菌株 | 注入方式 | 对应真实事故类 |
|---|---|---|
| M1 改 id | 把 `index.html` 里一个被 JS 引用的 `id` 改名 → `getElementById` 拿到 null，绑定静默失效 | 需求 132 |
| M2 反转 | 第一条 `===` → `!==`，语法成立、判断反向 | — |
| M3 掐初始化 | `DOMContentLoaded` → 永不触发的事件名，页面正常渲染但 init 从不执行 | 需求 140 |
| M4 断依赖 | 摘掉一个 `<script src="js/x.js">` 标签，HTML/CSS 都在、该模块行为静默消失 | — |

**流程**：候选任务 → 隔离复制 → 跑基线 → **只保留基线全绿的**（本来就在红的 AC
没有「有没有守住」这回事）→ 逐个注入菌株重跑同一份 AC 脚本。

**产出指标**：

```
AC 有效率（严格） = 产品断言真的变红的菌株数 / 菌株总数
AC 有效率（宽松） = passed 从 True 变 False 的菌株数 / 菌株总数
```

**为什么分两档**：严格 < 宽松，差值就是「页面确实坏了、但只有脚本错误跳出来」——
那部分实际是被 console 错误兜住的，不是 AC 的功劳。只报宽松值会虚高。

**实测结果（2026-09-24 首轮，10 任务 / 20 条守卫 AC / 35 菌株）**

```
菌株总数 35
  产品断言红（严格）  13  (37.1%)
  passed 翻假（宽松） 13  (37.1%)
  ★ 完全漏网          22  (62.9%)
逐条 AC 计量: 21/72 = AC 有效率 29.2%
```

按菌株拆开的漏网率（最有信息量的一列）：

| 菌株 | 漏网率 | 解读 |
|---|---|---|
| M2 反转 `===`→`!==` | **9/10 漏网** | 逻辑静默出错，AC 几乎完全瞎 |
| M1 改 id（需求 132 类） | 7/10 漏网 | 绑定静默失效，多数 AC 看不见 |
| M3 掐初始化（需求 140 类） | 3/6 漏网 | 「看得见点不动」的页面一半能漏 |
| M4 断依赖（摘掉一个 js 模块） | 3/9 漏网 | 结构性破坏相对最容易被抓住 |

**三条结论**

1. **AC 守得住「页面崩」，守不住「页面活着但行为错」**。
   现有 AC 断言绝大多数是 `assert_exists` / `assert_visible` 这类**存在性检查**，
   页面还在、元素还在，它们就继续绿 —— 哪怕逻辑已经反了。
2. **一个意外的好消息**：严格 = 宽松（13 = 13），**没有任何一次是靠脚本错误蒙混过关的**。
   AC 一旦触发，触发的是真实的产品断言信号。判定干净，覆盖不足 —— 后者才是主要矛盾。
3. **漏网的另一种解读要诚实标注**：M2 反转的是文件里**第一条** `===`，
   可能落在 AC 根本不关心的代码路径上 —— 那种漏网属于「AC 范围外」，
   不全等于「AC 弱」。所以 29.2% 应读作 **AC 行为覆盖的上界**，不是「AC 只有 29% 是对的」。

**改进指向**：AC 翻译提示词（`prompts/verify/ac_translator.md`）应要求生成
**行为性断言**（`assert_text` 含预期值、`assert_value`、`assert_canvas_change` /
`assert_dom_change`），而不是默认落到 `assert_exists`。
这与 P3（去实现依赖）改的是同一个文件，可以合并做。

**成本**：低。复用现有 eval 框架，注入是纯文本替换，跑的是已有的 `run_ac_checks`。

### P2.5：不可信失败的降噪（**新增，由 P0 实测得出**）

**问题**：45.3% 的 AC 是「脚本没跑成 + 断言失败」。这些 `failures` 是在**被半驱动坏的页面**
上产生的 —— 比如点击步骤超时没点成，后面的断言自然找不到元素。
coder 拿到这份清单会去修一个**根本不存在的问题**，白白烧掉一轮 repair。

**三条可能路线**

| 路线 | 做法 | 评价 |
|---|---|---|
| a 标注降权（推荐） | 给这类 AC 打 `compromised=True`，在 repair 提示词里明确「此失败优先级低于可信失败」 | 最小改动，不丢信号 |
| b 快速失败 | 步骤抛异常即中止该 AC，不再收集后续 `failures` | 干净，但会丢掉真实缺陷信号 |
| c 触发重译 | harness 错误占比过高时，打破首轮锁定重译 AC 脚本 | 修根，但要防漂移复发 |

**采纳 a + 条件性 c**：

- **a 是必做**：`failures` 保持不动（不丢信号），但结果里增加
  `"compromised": bool(failures) and bool(harness_failures)`，
  并在 `nodes.py` 的 `ac_results_text` 里显式标注 ⚠️ + 说明。
- **c 的条件**：单个任务内 `harness_errors` 占比 ≥ 50% 时，判定为「翻译失败」而非「产品缺陷」，
  带 harness 错误信息**重译一次**（限一次，且写回缓存）。
  首轮锁定的本意是防同一份代码结果漂移，不是防修翻译错误 —— 翻译错了就该重译。

**验证**：新增测试断言「步骤抛异常 + 后续断言失败 ⇒ `compromised is True`」。

**风险**：a 会让 repair 提示词变长；c 会打破「首轮锁定」的不变量，
必须限制重译次数上限 1 次，否则退化成每轮漂移。

### P3：AC 翻译去实现依赖

**问题**：`_translate_acs_to_scripts`（`nodes.py:820`）把 **`code_text` 喂给翻译模型**
（:834-846 还从中提取 selector 清单）。翻译器**看过实现**，会迁就实现，
甚至把 bug 当特性写进验证步骤 —— 相当于「作者验自己的代码」。

**改法（分两档，先做轻的）**：

- **轻档**：只喂 AC 文本 + **接口契约**（`id`/`class` 清单算接口，可以保留），
  **不喂 `code_text` 全文**（那是实现逻辑）。改动就是删一个参数。
- **重档**：派一个**没参与 coder 实现**的独立上下文 agent 翻译 AC。

**验证**：照搬项目已有的 `--with-memory` A/B 纪律 —— 加 `--ac-translate=isolated` 开关，
默认关，跑 21 题三遍，差距 <3 个百分点不下结论。

### P4：「AI 操作浏览器」可视化（**前置：P1/P2 完成**）

**价值判断**：这个卖点成立，但有个硬前提 ——

> **单引擎原则**：用户看到的那个浏览器，必须就是做出 PASS/NEEDS_WORK 判定的那个浏览器。

如果画面上的操作不是真正决定结果的那次执行，那就是**表演**，不能对外讲。

**为什么不需要换 Browser Use**：Browser Use 是**跑在 Playwright/CDP 之上**的，
它解决「下一步做什么」，不解决「怎么把画面显示给用户」。可视化靠的是
CDP `Page.startScreencast`，与用哪个引擎无关。换它对可视化**零帮助**。

**实现路径**：

| 需求 | 方式 |
|---|---|
| 画面 | `context.new_cdp_session(page)` → `Page.startScreencast`，帧为 base64 JPEG |
| 推前端 | 复用现有 SSE 通道（`nodes.py:1237` 的 `sse.checklist_update` 已在逐条推 AC 结果，缺的只有画面） |
| 接管 | `Input.dispatchMouseEvent` / `Input.dispatchKeyEvent` 转发前端事件，同时暂停自动化 |

**三条必须注意的成本**：

1. **带宽**：1280×800 JPEG q60 约 60–100KB/帧，10fps = 0.6–1MB/s/会话，3 并发打满上行。
   → **推关键帧而非连续流**：每个 AC 步骤执行前/后各一帧 + 步骤文字，形成「操作回放」。
   带宽降两个数量级，叙事反而更强。
2. **接管污染**：用户接管后页面状态脏了，后续 AC 从脏状态继续 → 结果不可信。
   必须「接管即作废本轮」或接管后 `_load()` 重置。
3. **并发**：每会话一条流，空闲必须停 screencast。headless 新版有渲染，不需要 headful/Xvfb。

**为什么不能走「前端 iframe 内驱动」的省钱路子**：那会产生**两套引擎互不通信**，
出现「画面上通过、判定却失败」，用户会当成 bug 报过来 —— **比现在更糟**
（现在至少判定是诚实的，只是用户看不见）。

## 6. 为什么不换 Browser Use / LLM 驱动 agent

| 层面 | 判断 |
|---|---|
| 驱动浏览器 | 可能略强（DOM 索引化比手写选择器抗漂移） |
| 做出判定 | **明显更弱** —— 不可重放，直接毁掉 req76 确定性回放 demo 与 21 题基线可比性 |
| 覆盖范围 | canvas 与跨域 iframe 结构性不支持，而旗舰演示正好在这两个上 |
| 项目哲学 | 平台的差异化恰恰是「确定性证据 > LLM 判断」，换引擎是自毁卖点 |

**但可以借它的思路**：DOM 索引化选元素，正好用来修 S3（`_resolve_selector` 张冠李戴）。
拿优点、挡不确定性在门外。
