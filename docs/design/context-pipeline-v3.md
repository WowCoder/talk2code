# 上下文管道 v3：记忆归因与终态瘦身

本文是 `context-pipeline-v2.md` 的增量改造说明。v2 解决的是「编码阶段上下文怎么裁剪」，
v3 解决的是可观测平台上暴露出来的**三个旁路缺陷**：记忆归因恒空、记忆重复注入、
终态对话历史不瘦身。

---

## 1. 背景：可观测平台暴露的三件事

上线 Admin 轨迹页后，从单条需求的完整事件流里能直接读出三个此前只能靠日志猜的问题。
取证自 `agent_events` / `memory_hits` / `requirements.dialogue_history` 三张表与
`ContextPipeline` 运行时日志。

### 1.1 记忆注入重复 4 次，且归因恒为 pending

一条走完「提交 → 澄清 → 确认计划」的需求，规划阶段会出现 4 条 `memory` 事件：

| 次序 | 触发 | 代码位置 |
|---|---|---|
| 1 | 首次提交 | `requirement_service.py` `process_requirement` 内注入点 |
| 2 | 澄清回答提交，整条流程重跑 | 同上 |
| 3 | 计划确认，`process_requirement` 先算一次 | 同上 |
| 4 | 约 130ms 后转断点恢复，又算一次 | `_continue_from_plan_checkpoint` 内注入点 |

**「每次命中的记忆都不一样」是界面误导**：4 次事件的 `hit_ids` 不同，但查
`memory_hits` 表会发现它们指向的 `memory_id` 是同一对。ID 递增只是因为
`_record_hits` 每次注入都新写一行记账记录，不是命中了不同内容。

第 3、4 条相隔仅约 130ms，是**双入口**导致的：`process_requirement` 在判断要不要转
`_continue_from_plan_checkpoint` **之前**就把记忆算好了，转过去之后又算一遍。

更严重的是归因回填：`resolve_hits(_memory_hit_ids)` 写在 `_process_final_state` 里，
而该方法的参数列表中**没有**这个变量 —— 它只存在于两个注入点的局部作用域。
于是每次调用必抛 `NameError`，被 `except` 静默吞掉，命中行的 `outcome` 永远是
`pending`。生产库里数百条命中记录无一例外，记忆归因在数据上完全无法回答
「注入的记忆到底有没有用」。

### 1.2 终态不瘦身，未完成需求的历史会膨胀一个数量级

`finalize_delivery` 目前**只在成功交付分支调用**。它做的事是：把 `thinking` /
`tool_call` / `system` 轨迹归档到 `.task/EXECUTION.jsonl`，再让 `dialogue_history`
只保留人类对话与瘦身后的迭代卡片。

后果是只对成功需求生效。实测对比：

| 需求终态 | `dialogue_history` 体积 |
|---|---|
| 成功交付 | 12 KB ~ 53 KB |
| 未完成（待确认 / 失败） | 110 KB ~ **210 KB** |

未完成需求的历史里，完整保留着全部 `read_file` / `write_file` / `edit_file` 原文
（单条可达数万字符）。用户在这类需求上继续对话时，`chat_with_requirement` 会把整段
历史塞进新一轮 state，其中 `tool_call` 类型是**会进入 prompt** 的。

### 1.3 一处需要更正的前期判断

先前认为「历史里 64% 是思维链，会污染 prompt」。核实 `_stage_history` 后更正：
`thinking` 与 `iteration_batch` **本来就已被过滤**，不进 prompt（`role == "thinking"`
和 `role == "iteration_batch"` 两处 `continue`）。

所以思维链占的是**存储体积**，不是 prompt 体积。真正的 prompt 增量来自 `tool_call`
结果，而它在未完成需求上没有被剥离 —— 1.2 才是主要矛盾。

### 1.4 压缩机制：已接入但从不触发

`ContextPipeline` 由 `runtime._build_messages` 调用，三层治理（L3a 单条截断 /
L4 预算遮蔽 / L5 兜底）都在主链路上，不是孤儿代码。

但运行时日志里近 25 条记录**全部**是 `masked=0 dropped=0 compacted=0`。原因是预算
24000 tokens，而实测 `head` 约 2400~3300、`history` 峰值不足 1000，差一个数量级，
永远撞不到线。

设计取舍：预算的作用是**兜底上限**，不是日常治理开关。在上下文规模健康时它本就不该
触发，因此本次**不调整预算**（触碰它需要重跑 eval 验证通过率，单独立项）。改做的是
让「已过滤掉多少」变成可观测数字，见 2.4。

## 2. 改造项

### 2.1 记忆归因回填（P0）

**现状**：`resolve_hits` 的实参不在 `_process_final_state` 作用域，必抛 `NameError`。

**方案**：记账行 id 经由 `final_state` 传递 —— 注入点写入 `state['_memory_hit_ids']`，
终态处理从 `final_state.get('_memory_hit_ids')` 读取。这样跨进程（Celery worker）也成立。

进程内再叠一层兜底：注入结果缓存按 `requirement_id` 留存，终态取不到时回退读缓存。

**验收**：`resolve_hits` 收到的 id 列表非空；跑完一条需求后，`memory_hits` 中对应行的
`outcome` 不再是 `pending`。

### 2.2 记忆注入幂等（P0）

**现状**：同一需求重复入队即重复检索、重复记账。

**方案**：加进程内缓存，key 为 `(requirement_id, 需求内容摘要)`。命中则直接复用上次的
`(block, hit_ids)`，**不再新写记账行**。

需求内容变化时（用户补充说明）摘要随之变化，自然重新检索，不会误命中旧结果。缓存按
LRU 上限回收，避免长驻进程内存无界增长。

**为什么是进程内而不是落库**：缓存失效的后果只是「多注入一次」，可接受；落库会引入
跨任务的一致性问题，收益不抵复杂度。

**验收**：一条走完澄清 + 确认的需求，`memory` 事件从 4 条降到 1 条，`memory_hits`
新增行数等于注入的记忆条数（而非其倍数）。

### 2.2b 惰性注入：从「入队即检索」到「用到了才检索」（P0）

幂等只解决了「同一份内容重复入队」，解决不了「这次入队压根用不到记忆」。实测 4 次降到
2 次之后剩下的那一次，**在被澄清门禁拦下的入队上仍然是完全浪费的**。

**根因**：注入点在 `process_requirement` 的**入队处**（构造 ToolCallLoop 之后立刻检索），
而这次入队能不能走到编码是不确定的：

| 入队 | 后续 | 记忆块是否被任何 LLM 消费 |
|---|---|---|
| 首次提交 | `team_leader_node` 的第一件事是澄清门禁（`nodes.py:698`），未经用户确认直接返回问题表单 | **否**，一个 turn 都没进 Coder |
| 澄清后重跑 | 走完规划、编码 | 是 |
| 计划确认 | `process_requirement` 跑约 130ms 就转 `_continue_from_plan_checkpoint` | 视路径而定 |

这些提前写下的记账行既没参与生成，也不会在终态之外被结算 —— 它们只做两件
坏事：把归因分母灌水，以及在界面的**规划**阶段插一条与本次生成无关的记忆事件。

**方案**：`_attach_lazy_memory` 只在 loop 上挂 provider，**第一个真正拼 system prompt 的
turn 才检索**。判据不是「猜这次会不会被门禁拦下」（门禁放不放行由 LLM 定，猜不准），
而是「有没有人真的要读它」—— 只有 Coder 的 prompt 与定向补全阶段会读，读的那刻才算。

**两个消费者的兼容性**：ToolCallLoop 的 `_build_system_prompt` 是包装（闭包在作用域内）；
但 `file_coder._inject_coding_context` 是**整体替换**，拿不到闭包，改为读
`loop._memory_provider` 触发；provider 缺失时（eval 侧直 call 的路径自己挂静态块）
退回读 `_memory_block`，行为不变。

**副作用（是修正不是退化）**：记忆事件的时间点从「规划阶段」后移到「编码首个 turn」。
注入本就只作用于编码，事件应该出现在它真的生效的地方。

**验收**：一次走完澄清 + 确认的完整需求，`memory` 事件 = 1 条，且出现在编码阶段。

### 2.3 终态统一瘦身（P0）

**现状**：`finalize_delivery` 只在成功分支调用。

**方案**：提到 `_process_final_state` 的入口处统一执行一次，覆盖所有终态分支
（执行错误 / 主动终止 / 验收未通过 / 成功交付）。

**为什么在入口而不是各分支内**：入口处一次调用即覆盖全部 return 路径，不会出现新增
分支时漏掉。各分支后续对 `dialogue_history` 的读写都发生在瘦身之后，语义不变。

**为什么安全**：`_archive_tool_trail` 是**归档**不是删除，轨迹原样落盘到
`.task/EXECUTION.jsonl`，排查能力不损失；`iteration_batch` 在瘦身中保留（仅压缩
arguments 长值），详情页编码过程照常展示。

**验收**：人为构造一个终止态需求，其 `dialogue_history` 不含 `role == "tool_call"`
消息，且 `.task/EXECUTION.jsonl` 存在且条数与原轨迹一致。

### 2.4 过滤量可观测（P1）

**现状**：`build()` 返回的 stats 只统计超预算后的遮蔽动作，对「本来就过滤掉的
thinking / iteration_batch」没有计数。于是从日志上看不出管道做了什么，这也是
「压缩机制好像不存在」这一印象的直接来源。

**方案**：stats 增加两个字段，记录被过滤的消息条数与对应 token 估算，并一并打进
`runtime` 的 `[ContextPipeline]` 日志行。

**验收**：一条普通需求的日志里能看到 `filtered=N`（N > 0），而 `masked/dropped/compacted`
仍为 0 —— 两者语义分离，前者是日常治理，后者是兜底。

### 2.5 预算估算口径修正（P1）

**现状**：`_build_messages` 把**完整** system prompt 传给 `pipeline.build` 做预算估算，
而实际进入 messages 的是剥离了可变尾段的 `stable_prompt`，估算系统性偏高。

**方案**：改传 `stable_prompt`，与真实落进 messages 的内容对齐。

### 2.6 编码历史软预算（L2.5 渐进治理）（P0）

> 归属说明：这是问题 2「每轮全量重发、噪声大」的正主之一，此前被错误划入
> 「范围外」，已收回。

**现状**：治理只有 24000 硬预算一层。常规需求全程 head 3.3K + history 4~8K，
**差一个数量级永远触发不了**；只有极端需求才撞线，且一撞就是猛的。中间没有任何
渐进 —— 「压缩机制在哪」这个问题的根源就在这。

**方案**：新增 `history_soft_budget`（默认 6000，`min(6000, budget)` 防两层打架）。
history（单独计，不含 head）超过软预算即开始按既有遮蔽机制从最旧的工具结果遮起，
复用同一套保护集（write/edit/验证结果永不遮、最近 3 条 read 不遮、preserve 不遮）。
遮蔽留下带「如需重新读取」指引的占位符，模型随时拿回内容 —— 是有代价标注的省略，
不是信息蒸发。

**明确不改的**：write/edit 结果的保护豁免。极端需求（req 33 实测 452K tok 历史）
遮完所有可遮候选后仍剩 177K，全部来自受保护的 write 正文 —— 解除这层保护让
「模型对文件现状的认知」从靠历史转靠文件索引 + 重读，是行为级变更，需 eval
验证通过率后再动。

**实测**（真实编码期历史，离线重放）：

| req | history tok | 硬预算-only 后 | 软预算渐进后 |
|---|---|---|---|
| 104 | 28,882 | 23,508 | **19,040**（-19%） |
| 31 | 104,120 | 44,404 | 44,404（可遮候选耗尽） |
| 33 | 452,412 | 177,289 | 177,289（同上，剩余全是受保护 write） |

### 2.7 第二轮对话背景瘦身（P0）

> 归属说明：问题 5「第二轮传全量」的正主，此前同样被错误划入「范围外」。

**现状**：Chat 修改路径把交付后的完整 `dialogue_history` 全量进 prompt。终态瘦身
解决了工具轨迹，但问题表单、编码轮旁白、交付 handoff、评估报告全文仍然全量
跟着走 —— 它们对「改点东西」没有价值。

**方案**：`condense_chat_background(history)` 确定性规则（无 LLM），runtime 仅在
`metadata.is_chat` 时套用，**只裁 prompt 视图不落库**（DB 里的完整对话流供 UI 展示）：

- 最后一条 user 消息**及其之后**原样保留（本轮诉求 + 本轮 turns，动它破坏累加）；
- `preserve=True` 保留（用户澄清答案、计划理解 —— 那是二轮的 SPEC）；
- 第一条 user 消息（原始需求）保留，超 1200 字符截断；
- agent 的「代码评估」只留结论段（600 字符）；
- 其余（表单 / 旁白 / handoff / 评估全文 / **背景里的 tool_call 残留**）丢弃。

**实测**（req 217 交付后历史 + 模拟第二轮诉求）：prompt 视图 1464 → 837 tok
（-43%）。若历史上还残留工具轨迹（未走终态瘦身的存量数据），降幅远大于此 ——
背景里的 `tool_call` 一律不保留。

**不做完全无状态 coder 的原因**：「编码只传 system+spec、历史零累加」是同一根
光谱的极端点。软预算 + 背景瘦身已把「进 prompt 的历史」约束在有限且渐进治理的
范围内，而完全无状态要求模型每轮靠读文件重建全部认知，迭代轮数与 token 总量
反而可能上升 —— 需要 eval 数据支撑，单独立项。

## 3. 明确不做

| 项 | 原因 |
|---|---|
| 调低 `budget` | 预算是兜底上限，下调会让压缩在常规需求上开始生效，直接影响生成质量。需要重跑 eval 验证通过率后单独立项 |
| 截断 `thinking_preview` | 它不进 prompt，只占存储；截断会直接影响前端「思考过程」展示，收益不抵体验损失 |
| 拆分 `coder_base.md` | system prompt 长度不是当前瓶颈（约 3K tokens）。前缀缓存已稳定命中，重构风险大于收益 |
| 给第二轮对话（Chat 修改路径）补记忆注入 | 该路径至今压根没接过记忆（`routes/requirements.py:454` 的 ToolCallLoop 没挂 provider）。是独立缺口，不属于本次重复注入治理范围 |

## 5. 实施结果

全量单元测试 **1117 通过**（新增 5 例守卫覆盖惰性注入），零回归。以下为生产 /
真实数据的实测结果。

### 5.1 记忆注入去重：4 次 → 2 次 → 1 次

同一条走完「提交 → 澄清 → 确认计划」的需求，两轮修复叠加后的结果：

| 阶段 | 改造前 | 幂等化后（2.2） | 惰性化后（2.2b） |
|---|---|---|---|
| 首次提交 | 注入 1 次 | 1 次 | **0 次**（被澄清门禁拦下，没进 Coder） |
| 澄清后重跑 | 注入 1 次 | 1 次（内容确实变了，应当重检索） | —（见下） |
| 计划确认（双入口） | 注入 **2** 次 | 0 次（内容未变，缓存命中） | — |
| 编码首个 turn | — | — | **1 次** |
| 合计 | 4 | 2 | **1** |

惰性化后注入点后移到编码开始前夕，时间线上只剩一条 `memory` 事件（req 219 的
`seq=7`，落在计划确认之后、第一个 `coding/llm_turn` 之前）。记账行从 5 行降到
**1 行**，与真实注入的记忆条数一致。

注：事件本身的 `stage` 标签仍是 `planning`（`event_contract` 里 `memory` kind 的
默认值），因为它发生在第一个 `coding` 事件之前。标签没跟着搬家，只是时间戳后移了。

### 5.2 归因回填：pending → 结算

改造后需求终态的命中行全部结算（req 218 的 5 条 → `pass`；req 219 的唯一 1 条 →
按 `qa_data['passed']` 结算），`resolved_at` 有值，pending 归零。
改造前同一位置的记录无一例外停在 `pending`。

> 排查提示：状态落库早于记忆回填约 3 秒。用脚本校验时若一看到终态就查，
> 会读到回填前的 `pending` 而误判为未生效。

### 5.3 终态瘦身：未完成需求 -75% ~ -84%

对真实需求的历史做一次瘦身（离线计算，不写库）：

| 终态 | 瘦身前 | 瘦身后 | 降幅 | `tool_call` 条数 |
|---|---|---|---|---|
| needs_user_input | 209,087 | 52,481 | **-75%** | 22 → 0 |
| needs_user_input | 213,991 | 51,096 | -76% | 20 → 0 |
| failed | 186,733 | 29,206 | **-84%** | 24 → 0 |
| finished_with_issues | 180,689 | 32,989 | -82% | 19 → 0 |
| finished（已瘦过） | 32,715 | 32,715 | 0% | 0 → 0 |

最后一行是幂等性验证：成功交付的需求二次瘦身无变化。

### 5.4 过滤量首次可见

生产日志（同一需求编码第 8 轮）：

```
[ContextPipeline] head=3324 head_sha=020613ac history=7931
filtered=14/16816tok masked_read=0 masked_nonfile=0 dropped=0 compacted=0
```

过滤掉 14 条、约 16.8K tokens，而实际发送的 history 只有 7.9K tokens ——
**被剥离的量是实际发送量的两倍多**，此前这一数字完全不出现在任何统计里。

`head_sha` 全程不变，说明稳定前缀拆分仍然有效（前缀缓存的前提）。

### 5.5 软预算与背景瘦身（2.6 / 2.7 实测）

离线重放真实数据（不写库），数据见 2.6 / 2.7 节表格。要点：

- 软预算在中等规模历史（req 104，28.9K tok）上即开始工作：23.5K → 19.0K；
  极端需求（req 33，452K）遮完可遮候选后剩余全是受保护的 write 正文，
